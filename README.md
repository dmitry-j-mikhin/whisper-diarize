# Транскрипция встреч

Локальная расшифровка записей встреч с разметкой говорящих. Ничего не уходит наружу:
[GigaAM](https://github.com/salute-developers/GigaAM) (или
[faster-whisper](https://github.com/SYSTRAN/faster-whisper), `--asr whisper`) и
[pyannote](https://github.com/pyannote/pyannote-audio) считают на видеокарте NVIDIA,
если она есть, иначе на CPU.

На выходе в `records/<имя записи>/` появляются:

| файл | что внутри |
|---|---|
| `<имя>.txt` | читаемый текст: абзац на реплику, с таймкодом и говорящим |
| `<имя>.srt` | субтитры |
| `<имя>.json` | сегменты, пословные таймкоды, границы реплик — вход для повторной обработки |
| `<имя>.log` | прогресс и диагностика |

Свою запись встречи — микрофон и собеседников отдельными дорожками — делает `./record.sh`,
см. «Своя запись встречи».

## Как пользоваться

```bash
./transcribe.sh "запись.webm"                  # расшифровка, русский
./transcribe.sh "запись.webm" --diarize        # + кто что сказал
./transcribe.sh "запись.mp4" -l auto -m medium # другой язык и модель полегче (это whisper)
./transcribe.sh "запись.mp4" --asr whisper     # whisper, даже когда сгодился бы GigaAM
```

Распознаёт по умолчанию GigaAM — час встречи за полминуты на видеокарте. Он знает только
русский, поэтому под другой язык, whisper-модель в `-m` или `--initial-prompt` скрипт сам
переключается на whisper и говорит об этом в лог. Подробнее — «Движок распознавания».

Первый запуск сам создаст `.venv` и поставит зависимости (~3 ГБ с CUDA-сборкой torch).
Видео на вход подавать можно любое — звук извлекается ffmpeg-ом, шестнадцать килогерц моно,
как ждут все модели.

Полезное:

* `--initial-prompt "NetBird, WireGuard, Keycloak"` — подсказка с терминами и именами,
  заметно улучшает написание жаргона (умеет только whisper, и запуск с ней уходит к нему);
* `--speakers 5` — если число участников известно, диаризация ошибается реже;
* `--keep-audio` — не удалять извлечённый `.wav` (нужен для повторных прогонов);
* `-m large-v3-turbo` — whisper примерно вдвое быстрее ценой качества;
* `-m v3_rnnt` — GigaAM без пунктуации и заглавных, голый текст;
* `--asr whisper` — распознавать whisper-ом: медленнее, но любой язык и подсказки терминами;
* `--batch-size 0` — выключить батчевый режим faster-whisper (на GPU он по умолчанию, 8 кусков
  за проход, вдвое быстрее). Текст в нём другой: лучше пунктуация и заглавные, но сегменты
  по 25–30 с вместо фраз и менее точные пословные таймкоды. Подробнее ниже.

## Своя запись встречи

Телемост идёт в браузере, и видео в расшифровке всё равно не участвует — поэтому рядом
лежит `record.sh`: он пишет только звук и сразу двумя дорожками.

```bash
./record.sh                      # пишем до Ctrl+C, имя записи — дата и время
./record.sh "планёрка"           # своё имя
./record.sh --app firefox        # «они» — потоки Firefox вместо всего выхода (на встречах не проверено)
./record.sh --stream "Звонок в Яндекс Телемосте"   # «они» — только поток вкладки звонка (на встречах не проверено)
./record.sh --list               # какие есть микрофоны и выходы
./record.sh --toggle [опции]     # фоном: не пишем — начать, пишем — остановить
./record.sh --stop               # остановить фоновую запись
./record.sh --status             # «recording <секунд> <имя>» или «idle»
./record.sh --auto [опции]       # сторож: вошёл в звонок Телемоста — пишем, вышел — стоп
```

В `records/<имя записи>/` появляются:

| файл | что внутри |
|---|---|
| `<имя>.mic.flac` | свой голос с микрофона |
| `<имя>.them.flac` | остальные участники — то, что играло в наушниках |
| `<имя>.flac` | смикшированное моно, вход для `./transcribe.sh` (`--no-mix` отключает) |

Врозь — чтобы убрать половину работы у диаризации: на своей дорожке не говорит никто
чужой, а на дорожке остальных нет тебя. Кто из двоих говорит — известно точно, делить
приходится только собеседников между собой.

### Как это устроено

`pw-record` поднимает в PipeWire два приёмника — по одному на дорожку — и **подписывает**
их на порты: первый на микрофон, второй на выход звука. Ничего не создаётся и никуда не
переключается: существующие связи не рвутся, в наушниках всё играет как играло, Телемост
слышит микрофон как обычно. Скрипт можно убить как угодно грубо — звук в системе останется
цел, отвалятся только лишние связи.

### Почему врозь, а не одним четырёхканальным узлом

Сначала обе дорожки снимались одним узлом — ради общих часов: сигнал, поданный сразу в обе
пары каналов, ложился с расхождением в ноль сэмплов. Пришлось отказаться: **узел,
связанный сразу с микрофоном и с выходом, склеивает два устройства в одну группу
PipeWire**. Ведущими становятся часы микрофона, выход из ведущего превращается в ведомого
и начинает подстраиваться под чужой клок — это пересогласование и слышно как треск, и у
себя, и у собеседников. В `pw-top` видно прямо: до записи ведущий — `alsa_output…`
(`QUANT 512`), а стоит подключить такой узел, ведущим становится `alsa_input…`, и выход
вместе с потоком браузера уезжает в ведомые (`+`). С двумя независимыми узлами ведущий не
меняется: приёмник «они» просто добавляется в группу выхода, приёмник «я» живёт в группе
микрофона, часы у каждого устройства свои.

Плата — дорожки начинаются не в один сэмпл: устройство микрофона поднимается дольше, чем
уже играющий выход (замеры: 10–20 мс; в прежнем заходе с двумя процессами набегало 85).
Зато кончаются они одновременно — оба приёмника гасит один `kill`, — поэтому микс сводится
**по хвосту**: которая дорожка короче, та сдвигается вперёд на разницу длительностей.
Разницу скрипт печатает в конце, микс собирается сразу после остановки (секунда-другая
на часовую запись). Ход часов входа и выхода на гарнитуре разъезжается на 11 ppm — 0,04 с
за час, для расшифровки и диаризации это ничто.

`--app firefox` цепляется к потокам браузера вместо общего выхода. **На встречах этот режим
не проверен**, а его прошлая версия 24.09 потеряла звонок: у Firefox все потоки зовутся
`Firefox`, и `pw-link` по имени «Firefox:output_FL» брал первый попавшийся — вкладку
мессенджера. Дорожка «они» вышла на −51 dB против −21 dB у записи всего выхода на той же
встрече. Теперь порты цепляются по id, каждый узел своей парой; на стенде (тон от второго
узла `Firefox` рядом с вкладкой MAX) тон в дорожку попадает — но это стенд, не встреча.

`--stream <кусок имени>` берёт не приложение, а поток: Firefox называет каждый поток по
заголовку своей вкладки (`media.name`), и у вкладки звонка это «Звонок в Яндекс Телемосте».
Так в дорожку идёт одна вкладка, без MAX и звуков соседних вкладок. На стенде 24.09 (три
потока `Firefox`: «звонок» с тоном 440 Гц, «другая вкладка» с 1000 Гц и настоящий MAX)
подключился только «звонок», 1000 Гц в дорожке нет. На встречах **не проверено**. Имя
потока Firefox меняет на лету вслед за заголовком (у MAX за день «MAX» → «2 непрочитанных
чата»); уже сделанные связи от этого не рвутся, но новый поток с другим именем не подцепится.

Проверен на встречах только весь выход — без `--app` и `--stream`. Потоки скрипт подцепляет
заново каждые две секунды: поток встречи пересоздаётся при перезаходе и смене устройства.

Оговорки:

* микрофон пишется сырым: эхоподавление, шумодав и автогромкость браузер делает у себя,
  в записи их нет. С гарнитурой это плюс — чистый близкий голос; с колонками в свою дорожку
  попадёт и эхо собеседников, тогда лучше `--mic` на источник с эхоподавлением;
* громкость наушников на дорожку «они» не влияет — монитор в PipeWire снимается до регулятора;
* в конце печатается средний уровень каждой дорожки: `-91 dB` значит, что писалось не то
  устройство или микрофон остался в мьюте.

### Кнопка в панели

Чтобы во время встречи не лезть в терминал, запись включается из waybar — индикатор стоит
рядом с громкостью. Серый микрофон — не пишем, красный кружок с таймером — идёт запись.

* **ЛКМ** — начать или остановить: пишется микрофон и всё, что звучит в текущем
  устройстве вывода, — так работает с любым созвоном, не только с Телемостом в Firefox;
* **ПКМ** — открыть папку с записями;
* старт и финал дублируются уведомлениями, в конце — длительность и куда легло.

Что для этого добавлено:

| файл | что в нём |
|---|---|
| `~/.config/waybar/scripts/meetrec-status.sh` | индикатор: читает файл состояния, отдаёт JSON |
| `~/.config/waybar/scripts/meetrec-toggle.sh` | клик: зовёт `record.sh --toggle` |
| `~/.config/waybar/config.jsonc` | модуль `custom/meetrec` и он же в `modules-right` |
| `~/.config/waybar/style.css` | стили `.idle` / `.recording` |

Кто сейчас пишет, лежит в `$XDG_RUNTIME_DIR/meetrec.state`
(его же читает индикатор), лог фонового запуска — в `$XDG_RUNTIME_DIR/meetrec.log`.
Запись, начатая кнопкой, отвязана от панели через `setsid`: перезапуск waybar её не уронит.
Индикатор перерисовывается по сигналу `RTMIN+11`, который шлёт сам `record.sh`, — поэтому
запись, запущенная из терминала, в панели тоже видна.

Три грабли, на которые это натолкнулось, — чтобы не наступить снова при правках:

* фоновый процесс наследует **игнорирование SIGINT**, поэтому `pw-record` останавливается
  сигналом TERM: INT до него просто не доходит, запись не прекращалась бы вовсе;
* дескриптор `flock` наследуется потомками, так что кнопка держала бы блокировку всю
  встречу и следующий клик молча не срабатывал — фоновый запуск идёт с `9>&-`;
* «пауза без sleep» через `read -t` на `/dev/null` возвращается мгновенно (EOF), и цикл
  перелинковки крутился вхолостую. Обычный `sleep` — то, что надо.

### Автозапись по звонку

Чтобы не помнить про кнопку, запись включает и выключает сторож — user-сервис
`~/.config/systemd/user/meetrec-auto.service` (`record.sh --auto [опции]`), он живёт
вместе с сессией sway. Вошёл в звонок Телемоста — запись пошла, вышел — через ~10 секунд
остановилась, с теми же уведомлениями и индикатором, что и у кнопки. Кнопка пишет весь
выход звука, а сторож с 24.09 запущен с `--stream "Звонок в Яндекс Телемосте"` (`ExecStart`
в юните) — это проверка записи одной вкладки на живых встречах, итогов пока нет. В первые
встречи 24.09 он писал с `--app firefox`, ещё до исправления, и на одной из них потерял звонок
в дорожке «они» (что случилось — выше, у `--app`).

Как он узнаёт звонок: Firefox называет свои аудиопотоки в PipeWire по заголовку вкладки,
а Телемост на время звонка ставит заголовок «Звонок в Яндекс Телемосте». Раз в 2 секунды
сторож ищет поток с таким именем среди воспроизведения и захвата микрофона
(`pactl list sink-inputs` / `source-outputs`). Проверено на тестовой встрече 2026-09-24:

* поток появляется уже на **экране проверки перед входом** — запись начинается оттуда;
* **мьют** в Телемосте потоков не закрывает, вход с выключенным микрофоном — тоже:
  Телемост держит микрофон открытым в любом случае, запись не рвётся;
* **выход кнопкой** и **закрытие вкладки** гасят потоки за секунду; страница после выхода
  и вкладка с чатами называются просто «Яндекс Телемост» и звонком не считаются;
* при переходе с экрана проверки во встречу потоки иногда пропадают на пару секунд —
  поэтому конец звонка засчитывается, только если его не видно 10 секунд подряд.

Как себя ведёт рядом с кнопкой:

* запись, **остановленная руками** посреди звонка, сама не возобновится — старт только
  на входе в звонок;
* запись, **начатая руками** до звонка или во время него, остановится с его концом;
* запись без звонка (не из Телемоста) сторож не трогает.

Управление: `systemctl --user stop meetrec-auto` — выключить до конца сессии,
`disable --now` — насовсем, `journalctl --user -u meetrec-auto` — что он решал и когда.
Другое имя потока — `MEETREC_CALL`, другая пауза до стопа — `MEETREC_GRACE` (секунды),
оба через `Environment=` в юните. Если Телемост в английском интерфейсе, заголовок другой:
посмотреть, как зовётся поток во время звонка, — `pactl list sink-inputs | grep media.name`.

### А отдельная дорожка на каждого участника?

На уровне звуковой системы — нет: до неё Телемост доходит уже сведённым в один поток.
Но сам он работает по схеме SFU, то есть браузер получает **отдельный аудиотрек от каждого
участника** и микширует их только у себя. Проверить на живой встрече: `about:webrtc` →
раздел с входящими RTP-потоками, сколько там audio — столько треков и приезжает.
Достать их можно только изнутри страницы — расширением или userscript, который перехватывает
`RTCPeerConnection` и пишет каждый трек своим `MediaRecorder`. Отдельная работа, в `record.sh`
этого нет.

## Где что лежит

Каталог на запись, всё про неё — внутри:

```
records/
  2026-09-11 12-00-30/
    2026-09-11 12-00-30.mp4            исходник
    2026-09-11 12-00-30.txt/.srt/.json расшифровка
    2026-09-11 12-00-30.log            лог прогона
    speakers.json                      кто под какой меткой на этой встрече
    2026-09-11 12-00-30.summary.md     что с ней делали дальше — саммари, разборы,
    ...                                страницы сравнения движков
```

Имя каталога — имя записи без расширения, имена файлов внутри его повторяют: так расшифровку
можно отправить кому-нибудь одним файлом, и по имени будет видно, откуда она.

Скрипт это делает сам: запись, брошенную в корень проекта, он переносит в её каталог и
дальше пишет туда же. Записи, лежащие где-то ещё (`~/Видео` и прочее), остаются на месте —
в `records/<имя>/` всё равно ляжет результат. Свой `-o` перебивает и то, и другое.

Весь `records/` — в `.gitignore` целиком: в репозитории только скрипты и README, данные
встреч наружу не уезжают. Поэтому же там нет правил вроде `*.json` — новую документацию
или пример конфига можно класть в корень, не воюя с игнором.

## Движок распознавания

По умолчанию считает [GigaAM](https://github.com/salute-developers/GigaAM) — конформер
Сбера под лицензией MIT, обученный только на русском (430 МБ против 3,2 ГБ у whisper
large-v3). По замерам авторов на русских датасетах он вдвое точнее: средний WER 8,3%
против 21,0% у whisper (их [таблица](https://github.com/salute-developers/GigaAM/blob/main/evaluation.md),
whisper там с нормализацией текста). По нашим замерам — прежде всего радикально быстрее,
и выбран он именно за скорость: на наших встречах модели расходятся на 13% слов, но
в слепом прослушивании спорных мест правы одинаково часто (см. «Что показало
прослушивание»).

Whisper никуда не делся и берётся сам, когда GigaAM не подойдёт: `-l` не русский,
в `-m` whisper-овская модель или задан `--initial-prompt`. Явно — `--asr whisper`.

```bash
./transcribe.sh "запись.mp4" --diarize                   # GigaAM v3_e2e_rnnt, с пунктуацией
./transcribe.sh "запись.mp4" -m v3_rnnt                  # голый текст без знаков и заглавных
./transcribe.sh "запись.mp4" --asr whisper --diarize     # whisper large-v3
```

Та же запись на 63 минуты, RTX A2000 8GB и i7-12700H:

| | whisper large-v3 | GigaAM v3_e2e_rnnt |
|---|---|---|
| распознавание на GPU | 2:00 (×26, батч 8) | 0:13 (×280, батч 16) |
| распознавание на CPU, 20 потоков | ~57 мин (×1,1) | ~3,7 мин (×17) |
| пик видеопамяти | 6,7 ГБ | 0,8 ГБ |
| вся расшифровка на GPU без диаризации | ~2,5 мин | 28 с |

Двадцать восемь секунд — это целиком: загрузка модели (3 с), нарезка по речи (8 с)
и распознавание (13 с). Диаризация после этого занимает свои 2,5 минуты и становится
самым долгим этапом. На CPU GigaAM обгоняет whisper в пятнадцать раз — час встречи
расшифровывается за четыре минуты и без видеокарты.

### Что меняется в тексте

Расхождение с whisper — 12,9% слов (для сравнения: два прогона whisper с разными
настройками расходятся на 4–10%, см. «Батчевый режим»). Разница не в одну сторону:

* **пунктуация и заглавные** — у `v3_e2e_rnnt` их столько же, сколько у батчевого
  whisper (29 знаков на 100 слов), модель ставит их сама; у `v3_rnnt` и `v3_ctc`
  текст голый, сплошным нижним регистром;
* **GigaAM пишет речь как она есть**: 9900 слов против 9250 у whisper. Лишние —
  это «э-э», «ну», повторы и оборванные слова, которые whisper молча причёсывает.
  Для протокола встречи это скорее минус, для разбора «кто что сказал» — плюс;
* **английские термины GigaAM чаще пишет кириллицей**: `concern partish nable` вместо
  `partitionable`, `вершнен скрипт` вместо `version script`. Латиницы в тексте 46 слов
  против 61 у whisper. Подсказать термины нечем: `--initial-prompt` у GigaAM нет;
* **числа** оба пишут вперемешку — то цифрами, то словами;
* **пословные таймкоды** у GigaAM систематически на 0,18 с позже, чем у whisper
  (медиана по 8151 совпавшему слову; p95 расхождения 0,6 с). На разрезание реплик
  по говорящим этого хватает, но границы чуть плывут.

Что из этого точнее по сути — по тексту не видно, эталонной расшифровки встречи нет.
Поэтому рядом лежит `compare_asr.py`.

### Чем сравнивать

```bash
cd "records/2026-09-11 12-00-30"
../../transcribe.sh "2026-09-11 12-00-30.mp4" --diarize                  # GigaAM
mv "2026-09-11 12-00-30.json" "2026-09-11 12-00-30.gigaam.json"
../../transcribe.sh "2026-09-11 12-00-30.mp4" --diarize --asr whisper    # whisper
../../compare_asr.py "2026-09-11 12-00-30.json" "2026-09-11 12-00-30.gigaam.json" --page
```

Печатает цифры (слов, латиницы, пунктуации, процент расхождения) и крупнейшие
расхождения, а с `--page` собирает локальный html: 60 случайных спорных мест,
в каждом кусочек звука и два варианта — **вслепую**, где чей, видно только по кнопке
«показать результат». Полторы минуты на десяток мест, и вместо «кажется, лучше»
получается счёт. Страница самодостаточная (звук внутри, base64), наружу не ходит,
ответы держит в localStorage браузера.

Из 851 места расхождения на нашей встрече 611 — по существу, остальное «э-э» и разбивка
слов; выборка на прослушивание берётся только из первых.

### Что показало прослушивание

Шестьдесят случайных спорных мест той же встречи, один слушатель:

| | |
|---|---:|
| верны оба варианта | 25 |
| мимо оба | 6 |
| прав GigaAM | 16 |
| прав whisper | 13 |

То есть в половине спорных мест спорить не о чем, а из 29 решающих GigaAM выигрывает
16:13 — разница в пределах случайности (двусторонний знаковый тест p = 0,7, 95% интервал
для доли GigaAM 37–73%). По качеству на наших встречах движки неразличимы, по скорости
отличаются в десять раз — отсюда и выбор по умолчанию.

### Ограничения GigaAM

* только русский. Английские вставки узнаёт, целиком английскую речь — нет.
  Есть `-m multilingual_large_ctc` на 70+ языков (2,2 ГБ), но пунктуации у неё нет,
  а на английском она слабее whisper;
* не понимает `--initial-prompt`, `--beam-size`, `--no-vad` и выбор языка. С первым
  и последним запуск просто уходит к whisper; если движок выбран явно (`--asr gigaam`) —
  скрипт предупредит и проигнорирует;
* длинную запись режет по речи не сама модель: нарезку на куски до 30 с делает
  VAD pyannote (`pyannote/segmentation-3.0`, gated — соглашение принимается один раз,
  как и для диаризации), поэтому pyannote и torch ставятся даже без `--diarize`;
* пакета на PyPI нет — точнее, лежит древний 0.1.0 без v3. Скрипт ставит из гита
  с `--no-deps`: пины пакета утащили бы torch и onnxruntime на версии назад.

## Имена вместо SPEAKER_00

Диаризация выдаёт безличные метки. Кто есть кто, видно по статистике и обращениям в тексте:

```bash
cd "records/2026-09-11 12-00-30"
../../rename_speakers.py "2026-09-11 12-00-30.json" --dump   # кто сколько говорил
cp ../../speakers.example.json speakers.json                 # вписать имена
../../rename_speakers.py "2026-09-11 12-00-30.json"          # подставить
```

`--map` не нужен: по умолчанию берётся `speakers.json` из папки с расшифровкой, то есть
именно этой встречи. Метки у каждого прогона диаризации свои, поэтому и файл свой.

Метки, которых нет в файле соответствий, останутся как есть — это правильное поведение
для кластеров, в которые diarization свалила реплики разных людей. Такому кластеру имя
давать нельзя, и лучше оставить его техническим.

## Переделать разметку, не пересчитывая

Границы реплик сохраняются в `.json`, поэтому менять логику резки можно бесплатно:

```bash
./transcribe.sh "records/встреча/встреча.webm" --diarize --diarize-only --reuse-turns
```

Секунда вместо полутора часов. Без `--reuse-turns` диаризация считается заново,
без `--diarize-only` — ещё и распознавание.

## Сколько это занимает

Замеры на записи 56 минут, RTX A2000 8GB Laptop (60 Вт), `large-v3` float16,
против CPU i7-12700H (20 потоков, int8, запись 50 минут):

| этап | GPU | CPU |
|---|---|---|
| извлечение звука | 4 с | 4 с |
| распознавание `large-v3` | 2,2 мин батчами (×26), 4,5 мин последовательно (×12) | 45 мин (×1.1) |
| диаризация community-1 | 2,5 мин | 44 мин |
| всего с диаризацией | ~5 мин | ~1,5 ч |

Это whisper; у GigaAM (движок по умолчанию) распознавание занимает 13 с вместо 2,2 мин
на GPU и 3,7 мин вместо 45 на CPU, и всё упирается в диаризацию — см. «Движок распознавания».

На GPU видеопамяти уходит до 6 ГБ, карта упирается в лимит мощности и греется до 87 °C,
поэтому скорость распознавания плавает от 21× в начале до 15× после прогрева. Процессор при
этом почти не считает: OpenMP-потоки torch и ctranslate2 только крутятся вхолостую на барьерах
между мелкими операциями (perf: 96% CPU-времени в `gomp_barrier_wait`). Поэтому на GPU
по умолчанию `--threads 1`: 1, 2 и 4 потока дают одно и то же время, 20 — на 5–10% медленнее
и вдвое-втрое больше CPU-времени. `--threads` — это всегда потоки CPU (OpenMP-пул torch и
ctranslate2); на CPU-пути они и делают всю математику, там уменьшать их не надо.

### Батчевый режим

На GPU включён по умолчанию (`--batch-size 8`): распознавание 1:59 вместо 4:28 на той же
записи, пик видеопамяти 6,7 ГБ. Размер не обязан быть степенью двойки: 10 влезает (7,6 ГБ
из 7,7, 1:54, текст тот же), 12 и 16 уже нет. Запас в 100 МБ того не стоит, поэтому 8.
Выключается `--batch-size 0`.
Что меняется в тексте (сравнение с двумя последовательными прогонами):

* два последовательных прогона сами расходятся между собой на ~4% слов — там, где whisper
  уходит в temperature-fallback, декодирование случайное (перебивания, шум);
* батчевый расходится с последовательными на ~10%, из них ~8% на участках, где последовательные
  между собой согласны. Это не обязательно ошибки: в крупнейших расхождениях батчевый находит
  реплики, которые последовательный пропустил, и лучше пишет английские термины
  (`elasticsearch`, `walking skeleton`), но местами и наоборот;
* пунктуации вдвое больше (29 знаков на 100 слов против 15), заглавных тоже;
* сегменты — куски VAD по 25–30 с, а не фразы; пословные таймкоды грубее (p95 ошибки 0,5 с
  против 0,15 с), так что резка по говорящим на перебиваниях получается рванее.

Эталонной расшифровки нет, поэтому «лучше/хуже» по смыслу можно судить только на слух.
Последовательный режим при temperature-fallback сэмплирует случайно; чтобы прогоны были
воспроизводимы, seed ctranslate2 зафиксирован.

### Тип вычислений на GPU

`--compute-type` на этой карте скорость не меняет, только память и текст (батч 8, та же запись,
сравнение с float16):

| тип | распознавание | пик VRAM | отличие текста от float16 |
|---|---|---|---|
| `float16` (по умолчанию) | 1:59 | 6,7 ГБ | — |
| `int8_float16` | 1:58 | 4,9 ГБ | 1,8% слов, местами заметно хуже |
| `bfloat16` | 2:03 | 6,7 ГБ | 6,5% слов, выпадают целые фразы |
| `float32` | не влезает | >8 ГБ | — |

Батч 16 не влезает и в int8. Whisper на GPU упирается не в арифметику, а в задержки
авторегрессионного цикла, поэтому int8 экономит только память.

float32 без батча: веса 6,2 ГБ, декодирование идёт на 7,6 ГБ из 7,7 и падает по памяти
на окне с temperature-fallback (там несколько дополнительных проходов). С `--beam-size 3`
досчитало за 8:30, вдвое медленнее float16, с beam 1 и 5 упало. Текст от float16 отличается
на 13% слов, ровно как два любых последовательных прогона с разной нарезкой окон, выигрыша
в качестве не видно. Не стоит того.

Пословные таймкоды практически бесплатны, поэтому включены по умолчанию: без них нельзя
разрезать реплику, внутри которой собеседника перебили. Отключаются флагом `--no-words`.

## Ограничения

Сегменты распознавания нарезаны по паузам, а не по говорящим (у whisper — по его VAD,
у GigaAM — кусками до 30 с). Скрипт режет их по границам
реплик, опираясь на пословные таймкоды, и сглаживает короткие вкрапления — но качество
упирается в саму диаризацию. Короткие реплики разных людей она порой сваливает в один
кластер, и разрезание такое не лечит.

## Модель диаризации

По умолчанию — `pyannote/speaker-diarization-community-1` (нужен `pyannote.audio>=4`).
Это gated-модель со статусом `gated: auto`: один раз зайдите на её
[страницу на HuggingFace](https://huggingface.co/pyannote/speaker-diarization-community-1)
залогиненным и примите соглашение — после этого токен качает её сам. Токен берётся
из `HF_TOKEN` или переменной `HUGGING_FACE` в `~/.tokens`.

Старую `speaker-diarization-3.1` можно выбрать флагом `--diar-model
pyannote/speaker-diarization-3.1`; если в окружении стоит `pyannote.audio<4`,
скрипт сам откатывается на 3.1 (с заглушками совместимости для свежих torch/torchaudio).
На практике разница между community-1 и 3.1 на обычной встрече невелика — community-1
чуть чище отсеивает шумовые микро-кластеры и активнее развивается.

## Зависимости

ffmpeg, python3. Остальное (`gigaam` из гита, `faster-whisper`, `pyannote.audio>=4`,
torch) скрипт ставит сам при первом запуске: CUDA-сборки, если `nvidia-smi` видит
видеокарту, иначе CPU-сборки. Лёгкая установка — только с `--asr whisper` и без
`--diarize`: тогда хватает одного `faster-whisper` без torch и pyannote.

### Видеокарта

Устройство выбирается автоматически (`--device auto`): cuda, если ctranslate2 видит GPU,
иначе cpu. Принудительно — `--device cpu` или `--device cuda`. Тип вычислений по умолчанию
`float16` на GPU и `int8` на CPU, меняется через `--compute-type`.

Что нужно от системы (Fedora, RPM Fusion):

```bash
sudo dnf install akmod-nvidia xorg-x11-drv-nvidia-cuda   # драйвер + libcuda; Secure Boot выключен
nvidia-smi                                               # после сборки модуля akmods (пара минут)
```

Если драйвер появился позже venv, скрипт сам переставит torch CUDA-сборкой (~3 ГБ).
Нюанс с версиями: ctranslate2 из PyPI ищет `libcublas.so.12`, поэтому torch берётся из индекса
`cu129` (индекс `cu130` приносит cuBLAS 13 и не подходит); библиотеку скрипт подгружает
из pip-пакета `nvidia-cublas-cu12` сам, `LD_LIBRARY_PATH` не нужен.

На ноуте с sway: компоситор отказывается стартовать при загруженном модуле `nvidia`,
лечится в `~/.config/sway/environment` (экран остаётся на Intel, NVIDIA только считает):

```
SWAY_EXTRA_ARGS=--unsupported-gpu
WLR_DRM_DEVICES=/dev/dri/by-path/pci-0000:00:02.0-card
```
